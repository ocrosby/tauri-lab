# CLAUDE.md — guidance for AI assistants working in tauri-lab

This file is the operating manual for Claude (or any coding assistant) when working in this repo. Read it before doing anything substantive.

## What this repo is

A learning lab. Each `apps/NN-*` directory is a **self-contained Tauri 2 demo** that isolates **one capability** (commands, events, filesystem, windows, tray, HTTP, etc.). The goal is pedagogical clarity, not production polish.

**Every demo is intentionally minimal.** Do not add features, refactor for abstraction, or introduce shared code between demos. Duplication across demos is a feature, not a bug — a reader should be able to `cd apps/NN-*` and understand the whole app without following imports elsewhere.

## Non-negotiable constraints

Violating these breaks the value proposition of the repo. If a change would require breaking one, stop and surface the trade-off rather than proceeding.

1. **No frontend build tooling.** Frontends are plain HTML/JS/CSS. No Vite, no React, no TypeScript, no Tailwind, no `node_modules`. Users must be able to run demos with `cargo tauri dev` and nothing else.
2. **`withGlobalTauri: true` in every `tauri.conf.json`.** This exposes `window.__TAURI__` so vanilla JS can `invoke`/`listen` without importing `@tauri-apps/api`.
3. **One capability per demo.** Do not bundle unrelated features. If a demo needs a new capability to work, that capability is a new demo.
4. **Every demo has its own `README.md`.** Explain what the demo teaches, what to click, what to observe.
5. **Capabilities files are minimal.** Grant only the permissions the demo actually uses. `docs/security.md` explains the model.
6. **Tauri 2.x only.** Do not add v1-style `allowlist` config or v1 plugin APIs.

## Directory conventions

```
apps/NN-name/
├── README.md
├── src/                    # frontend, served as static files
│   ├── index.html
│   ├── main.js
│   ├── style.css
│   └── vendor/             # only for demos that vendor a library (Three.js)
└── src-tauri/              # Rust backend
    ├── Cargo.toml          # unique package name matching demo directory
    ├── tauri.conf.json     # identifier: com.tauri-lab.<name>
    ├── build.rs
    ├── capabilities/default.json
    ├── icons/              # generated by scripts/generate-icons.sh
    └── src/
        ├── main.rs         # thin: calls into lib::run()
        └── lib.rs          # all the interesting code
```

The `main.rs` / `lib.rs` split is the Tauri 2 convention — `lib.rs` is what mobile targets link against. Do not merge them back into a single `main.rs`.

### Vendoring frontend libraries

When a demo needs a third-party JS library that isn't installable without a bundler (Three.js is the canonical case), commit the library file(s) under `apps/NN-name/src/vendor/<lib>/`. Rules:

- **Pin the version.** Record it in the demo README (e.g. "Three.js r170").
- **Per-demo copy.** Do NOT symlink or share across demos — Windows symlink support is unreliable and cross-demo coupling defeats the self-contained principle.
- **Reference via importmap in `index.html`**:
  ```html
  <script type="importmap">
    { "imports": { "three": "./vendor/three/three.module.min.js" } }
  </script>
  ```
  Then in JS: `import * as THREE from "three"`.
- **Vendor only what the demo uses.** If `08-threejs-basics` doesn't need OrbitControls, don't ship it in that demo's `vendor/`. Each vendor file must be justifiable per demo.

## Running demos

```bash
cd apps/NN-name
cargo tauri dev
```

Or from `src-tauri/`. Both work.

Prerequisites are listed in the root `README.md`. If a demo won't run, check:

1. Did the user run `./scripts/generate-icons.sh`? Icons are gitignored — a fresh clone has none.
2. Is the Tauri CLI installed? `cargo install tauri-cli --version "^2.0.0" --locked`.
3. Are platform build deps present? (`xcode-select --install` on macOS, `webkit2gtk` on Linux.)

## When adding a new demo

Follow `CONTRIBUTING.md`. Short version:

- Copy `apps/01-hello-world/`
- Renumber, rename the package in `Cargo.toml`, update `identifier` in `tauri.conf.json`
- Add ONLY the plugins / permissions this demo needs
- Write a short `README.md`
- Add a row to the demo table in the root `README.md`

## When editing an existing demo

- **Preserve minimalism.** If the fix requires more than a dozen lines of new code, ask whether the demo is now trying to teach two things.
- **Preserve permission scoping.** Never widen a capabilities file beyond what the demo uses.
- **Do not add dependencies to `Cargo.toml`** without a specific feature the demo needs. Each demo's dependency list is auditable at a glance — keep it that way.
- **Do not add framework imports to the frontend.** If a demo needs richer UI, the answer is "don't"; the demo is teaching Tauri, not UI.

## Rust conventions

- Format with `cargo fmt` (default settings).
- Lint with `cargo clippy -- -D warnings` before considering a demo done.
- Use `tauri::command` for IPC-exposed functions; keep them small — real logic goes in a helper function that a unit test can call.
- Managed state via `tauri::State<T>` with `Mutex`/`RwLock` for interior mutability — see `apps/02-ipc-commands`.
- Errors returned to JS must implement `serde::Serialize`. The standard pattern is a `#[derive(Debug, thiserror::Error, serde::Serialize)]` enum; if a demo needs error types, add them per-demo.

## Frontend conventions

- ES modules only (`<script type="module">`).
- No transpilation. Target modern evergreen APIs — Tauri's webview supports them.
- Destructure Tauri APIs at the top of `main.js`:
  ```js
  const { invoke } = window.__TAURI__.core;
  const { listen, emit } = window.__TAURI__.event;
  ```
- Keep DOM manipulation direct (`document.getElementById`, `element.textContent = ...`). No virtual DOM libraries.

## Documentation

`docs/` holds reference material shared across demos:

- `getting-started.md` — install + first run
- `architecture.md` — process model, IPC, permissions overview
- `ipc-commands.md` — command / event / state patterns
- `security.md` — capabilities, CSP, scoped plugins
- `packaging.md` — signing, notarization, installers
- `troubleshooting.md` — common errors

When a demo teaches a concept that belongs in `docs/`, put the concept in `docs/` and let the demo README link to it. Do not duplicate.

## What NOT to do

- **Do not run `create-tauri-app`** to scaffold new demos. It pulls in Vite + a framework, which violates constraint #1. Copy `apps/01-hello-world/` instead.
- **Do not add a workspace `Cargo.toml`** at the repo root. Each demo is independent; a workspace couples build times and lock files.
- **Do not consolidate `tauri.conf.json` files.** Config duplication is the price of demo independence.
- **Do not commit `target/`, `node_modules/`, `dist/`, or icon binaries.** All in `.gitignore`.
- **Do not commit `Cargo.lock`.** These are demo apps, not libraries or binaries with reproducibility guarantees; the root `.gitignore` excludes them.
- **Do not fetch vendor libraries from a CDN at runtime.** Vendor into `src/vendor/` and pin the version.
- **Do not share vendored libraries between demos** via symlink or config trickery. Each demo owns its copy.

## When the user says "add a demo for X"

1. Check whether X is already covered (grep `apps/*/README.md`).
2. Check whether X requires a Tauri plugin. If yes, add it to the demo's `Cargo.toml` and register it in `lib.rs` — never at the repo level.
3. Copy `apps/01-hello-world/`, rename, and build up minimally.
4. Add a row to the root README table.
5. Update `docs/` only if X introduces a concept not yet documented.
